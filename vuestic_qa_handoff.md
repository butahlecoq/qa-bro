# Handoff: Vuestic Admin как второй стенд для QA-агента

Дата: 22 ноября 2026 года. Версия: 1.0.  
Адресат: код-агент, реализующий расширение локального харнесса.  
Статус: задание на разработку; браузерные тесты этого стенда ещё не выполнены.

**Цель:** подключить текущее публичное демо Vuestic к QA-харнессу на Pi и opencode browse, выполнить проверки пользовательского CRUD и исследовать перенос процедур из Sakai.

**Архитектура:** один worker последовательно выполняет тесты через существующие браузерные инструменты; отдельная explorer-сессия извлекает навыки из реальных трасс. Три профиля знаний позволяют различить работу с нуля, перенос опыта Sakai и пользу собственного опыта Vuestic.

**Стек:** существующий Pi-харнесс, настроенная open-source модель, Chrome, Rust runtime opencode browse, MCP. Тестируемое приложение — Vue 3 + Vuestic UI.

Документ самодостаточен. Предыдущий `sakai_vue_qa_handoff.md` полезен для повторного использования модулей и исходных обучающих трасс, но не обязателен для понимания этого задания.

## 0. Инструкция код-агенту и приоритет решений

Реализуй поддержку **https://admin-demo.vuestic.dev/users** в существующем харнессе. Начни с проверки доступного browse и наблюдения живой страницы, затем выполняй задачи раздела 12. Используй уже работающие сессии Pi, hooks, лимиты, evaluator и хранение трасс.

Последнее решение заказчика: **публичное меняющееся состояние допустимо; локальная копия, закрепление deployment и полный reset не требуются.** Основная цель первого опыта — адаптация агента и перенос полезных процедур.

Для Vuestic этот документ заменяет следующие предположения первого handoff по Sakai:

| Вопрос | Решение для Vuestic |
|---|---|
| Основной стенд | Текущее публичное демо |
| Исходная база | Может меняться между попытками и во время работы |
| Подготовка попытки | Новая Pi-сессия, проверка текущего UI и уникальные собственные данные |
| Reload | Повторное чтение через UI; не reset серверных данных |
| Параметры между режимами | Одинаковая структура и сложность; разные уникальные идентификаторы |
| Сравнение | Небольшой описательный пилот, без требования статистической значимости |
| Старый тег Vuestic v4.0.0 | Не использовать как основной путь: у него другая модель хранения |
| Изолированная копия и mock backend | Не являются задачами этого этапа |

Не переносить reset-логику Sakai на Vuestic. При недоступном публичном backend сохранить точный блокер; не подменять стенд другой версией и не объявлять неисполненные тесты успешными.

## 1. Фиксированные ограничения

- Взаимодействие выполняется через установленный opencode browse с Rust runtime. Playwright не устанавливать и не возвращать в стек.
- Модель и её провайдер уже выбраны заказчиком; использовать текущую конфигурацию.
- Worker и explorer — отдельные сессии Pi с собственными промптами и доступами.
- Лимит LLM-вызовов сохраняется; браузерные действия и общее время попытки тоже ограничиваются конфигурацией.
- Все артефакты харнесса сохраняются локально у тестировщика.
- Для первой версии достаточно одного worker и выделенной вкладки существующего Chrome. Общий профиль и cookies допустимы.
- Извлечение, проверка, активация и отклонение навыков автоматические, без обязательного человеческого review.
- Ожидаемые результаты тестов фиксируются до запуска. Навык не может менять проверки.
- Агент работает с собственными записями попытки. Чужие записи не нужны для очистки или подготовки.
- Создание тестового пользователя в интерфейсе Users не означает регистрацию реального аккаунта. Отправка писем и приглашений в сценарии не входит.

Для этого задания не нужны многоплатформенный registry, векторный поиск, постоянный explorer, новая библиотека браузерной автоматизации или универсальный язык рецептов.

- Дополнительная страница Projects: https://admin-demo.vuestic.dev/projects
- Репозиторий: https://github.com/epicmaxco/vuestic-admin
- Описание проекта: https://admin.vuestic.dev/

Исследован commit **`9c5b44f3674d4c3e7ad01cc043d5331cee953c49`** ветки master. В его package указаны Vue `3.5.8` и Vuestic UI `^1.10.2`. Это версии исследованных исходников, а не утверждение о точной сборке публичного сайта. [V1, V2]

По исходникам маршруты Users и Projects не требуют предварительного входа. Для первого запуска сразу открывать /users; реальное поведение deployment проверить наблюдением. Если появился экран входа или отказ доступа, зафиксировать новое условие. [V3]

Изучены исходники, маршруты и доступность HTML публичной страницы. **Полноценного браузерного CRUD при подготовке handoff не было.** Ни успешная запись в backend, ни работоспособность всех действий на публичном deployment пока не подтверждены.

Код-агент может читать исходники для интеграции и подготовки проверок. Runtime worker и explorer получают сценарии, параметры, браузерные наблюдения и трассы. Не передавать им этот handoff целиком как промпт: он содержит сведения, полученные из исходников.

## 3. Что известно о текущем Users

### 3.1. Форма и навигация

| Элемент | Поведение по исходникам |
|---|---|
| Открыть создание | `Add User` |
| Диалог создания | `Add user`; подтверждение — `Add` |
| Поля | `Full name`, `Username`, `Email`, `Projects`, `Role`, `Active`, `Notes` |
| Обязательные поля | Full name, Username, Email; у Email дополнительно проверяется формат |
| Значения по умолчанию | Role = User, Active = true, Projects = [] |
| Notes | Текстовая область без объявленной обязательности или maxlength |
| Редактирование | Кнопка строки с aria-label `Edit user`; диалог `Edit user`; кнопка `Save` |
| Отмена формы | `Cancel`; при текстовых изменениях может появиться подтверждение потери изменений |
| Удаление | Кнопка строки с aria-label `Delete user` |
| Подтверждение удаления | `Delete user`; текст с именем записи; кнопки `Delete` и `Cancel` |
| Search | Поиск по подстроке Full name без учёта регистра; не по email/username |
| Фильтр состояния | Active / Inactive; исходно Active |
| Notes в таблице | Отдельной колонки нет; проверять через повторное открытие Edit |

Основания: форма, таблица, страница, валидаторы и загрузка данных. [V4–V8]

В первой версии оставить Projects пустым, аватар не загружать, Role = User и Active = true. Это уменьшает зависимость базового CRUD от связанных объектов. В исследованном коде пустой массив проходит клиентский валидатор `required`, реализованный через `!!v`; фактическую серверную проверку подтвердить smoke test. [V5, V8]

Кнопки подтверждения потери несохранённых изменений приложение явно не именует: они приходят из компонента. Их подписи нужно наблюдать, а не придумывать.

### 3.2. Особенности, влияющие на проверку результата

Текущие функции Users выполняют HTTP-запросы GET/POST/PUT/DELETE. Адрес API берётся из `VITE_API_BASE_URL`. Перезагрузка страницы не должна рассматриваться как очистка созданных объектов. [V7, V11]

Выявлены следующие свойства исходников:

1. **Закрытие формы не доказывает завершение сохранения.** Обработчик события запускает асинхронное сохранение и закрывает модальное окно, не ожидая его завершения. [V4]
2. **Уведомление не заменяет проверку данных.** В Add/Update success обычно следует за ожиданием API, но состояние прежней ошибки может влиять на уведомления. [V4, V9]
3. **Удаление особенно требует повторного чтения.** API-функция возвращает Response без проверки `response.ok`. Store воспринимает полученный Response как успех и убирает строку; сообщение об удалении тоже не является надёжным доказательством серверного эффекта. [V4, V7, V9, V10]
4. **Счётчик и текущая фильтрация могут отставать от изменений.** Мутации меняют локальные items, но не гарантируют соответствующее обновление total и повторное применение фильтра. [V10]
5. **После reload нужно заново выставить фильтр и поиск.** По умолчанию восстанавливаются Active и пустая строка поиска. [V9]
6. **Изменение Search инициирует загрузку.** Промежуточное состояние во время ввода не является окончательным результатом поиска. [V9]

Это основания для дополнительных UI-наблюдений. Если публичная сборка уже исправила указанные особенности, проверки всё равно остаются полезными. Не патчить приложение, чтобы получить желаемый результат теста.

## 4. Первый запуск: проверить текущие возможности

### Интеграция

Код-агент должен определить реальные схемы MCP `tools/list`, способ выбора вкладки и доступные способы:

- наблюдать страницу;
- нажимать кнопки, вводить значения и читать текущие значения полей;
- ждать состояния UI;
- перезагружать выделенную вкладку;
- сохранять сырой результат инструмента и evidence.

Набор инструментов browse зависит от установленной версии и режима выдачи. В исследованном runtime есть отдельные действия и `execute` на QuickJS; нельзя предполагать полную Playwright API или Node.js внутри `execute`. [B1, B2]

Сохранить версию browse, фактические схемы, модель, параметры генерации, viewport, URL и идентификатор вкладки. Не менять настройки общего relay и не перезапускать весь браузер ради этого опыта, если уже доступных возможностей достаточно.

### Smoke test

1. Открыть /users, получить наблюдение таблицы и текущих фильтров.
2. Открыть Add User, проверить доступность основных полей.
3. Проверить валидацию Email и возможность закрыть форму с отказом от несохранённых изменений.
4. Создать одну собственную запись и выполнить повторное чтение по правилам раздела 6.
5. Удалить её через UI и проверить отсутствие после повторного чтения.

Smoke — диагностическая фаза. Сохранить её отдельно. Если её трасса позже используется для обучения, явно назначить ей роль training; не передавать её скрыто в режим «без знаний».

При доступном UI и неработающем backend можно закончить интеграционный код и получить результаты валидации формы. CRUD и перенос в таком случае остаются непроверенными. Автоматические повторные попытки ограничены бюджетом.

## 5. Собственные данные и меняющееся окружение

Перед попыткой харнесс материализует параметры, сохраняет их в файл и передаёт worker. Для каждого нового полного запуска используются новые значения.

| Параметр | Правило |
|---|---|
| Full name | `QA ` + уникальный маркер run/attempt с случайным суффиксом |
| Username | Короткая последовательность латинских букв/цифр с тем же уникальным маркером |
| Email | Уникальный адрес вида `qa.<marker>@example.test`; письма не отправляются |
| Notes | 100 ASCII букв/цифр, сгенерированных до попытки |
| Updated Notes | Другая строка из 100 ASCII букв/цифр |
| Role | User |
| Active | true |
| Projects | Пусто |
| Avatar | Без загрузки |

Длина 100 символов — выбранное тестовое значение, а не предположение об ограничении поля. Если backend отвергает допустимые по исходникам данные, сохранить отказ и отдельно уточнить фактический контракт; не выдавать отказ за успех.

Уникальность важнее совпадения параметров разных режимов. Между режимами сохраняются длины, набор полей и правила генерации, а имена и email различаются. Seed можно записывать для диагностики; точное воспроизведение общей базы не требуется.

Notes сравнивается как точная строка. Role проверяется как роль `user` с наблюдаемой меткой User, Active — как булево состояние checkbox; различие регистра метки роли не означает другую роль.

### Правила идентификации

- Поиск выполняется по маркеру Full name.
- Перед редактированием или удалением сверяются точные Full name и Email; Username служит дополнительной проверкой.
- Одно только положение строки, частичное совпадение имени или общий префикс `QA` недостаточны.
- Backend ID, если он наблюдаем доступными средствами, записывается как дополнительная привязка. Не генерировать его за приложение.
- При нуле, нескольких совпадениях или противоречивых полях сначала получить дополнительное наблюдение.
- Параметры не меняются при восстановлении внутри одной попытки. Новый случайный суффикс после каждого timeout создавал бы риск дубликатов.

Параллельные изменения других записей допустимы. Они не требуют пересоздания стенда и не разрешают ослаблять ожидания для собственной записи.

### Завершение и очистка

После завершения теста удалить созданную им запись через UI, если она ещё существует и однозначно идентифицирована. У теста удаления эта операция уже является основным действием.

Очистка остальных тестов записывается отдельной фазой: `cleanup_status = done | not_needed | pending | failed`. Её сбой не переписывает историю основных проверок. Если удалить объект не удалось, сохранить его параметры в `pending-cleanup.json`, ограничить повторы и показать это в отчёте.

## 6. Контракт повторного чтения через UI

Общий helper `readOwnUserFresh` описывает процедуру наблюдения, а не прямой вызов REST API:

1. Дождаться завершения известной текущей операции либо зафиксировать, что её эффект пока неизвестен.
2. Перезагрузить только выделенную вкладку /users.
3. Дождаться загрузки страницы и таблицы.
4. Выставить нужный фильтр Active/Inactive и заново ввести полный маркер имени.
5. Дождаться результата именно этого поиска.
6. Проверить точные поля найденной строки; для Notes открыть Edit и прочитать текущее значение.
7. Закрыть форму без изменений.

Для доказательства отсутствия обязательно выполнить завершённый поиск по тому же маркеру в обоих фильтрах — Active и Inactive. Отсутствие только в ожидаемой вкладке недостаточно: запись могла сменить статус. Найденная в другом фильтре собственная запись возвращается как found с фактическим Active; evaluator отдельно проверяет соответствие ожидаемому состоянию.

Результат helper:

```text
found       — однозначно найдена собственная запись и получены её значения
not_found   — завершён поиск в Active и Inactive, соответствующей записи нет
ambiguous   — несколько кандидатов или противоречивые признаки
read_failed — загрузка/поиск не подтверждены, ошибка инструмента или приложения
```

`read_failed` и `ambiguous` нельзя превращать в `not_found`. Спиннер, пустая ещё не загрузившаяся таблица и ошибка GET не доказывают отсутствие записи.

Если доступно наблюдение сетевых статусов, оно помогает отличить завершённое чтение от ошибки загрузки. Содержимое записи и основные ожидаемые результаты проверяются через UI. Не добавлять в worker прямой REST CRUD, запись в Pinia/Vue state или вызов внутренних обработчиков.

Повторное чтение не гарантирует транзакционную изоляцию публичного сервиса. Оно даёт более сильное доказательство, чем сообщение об успехе или изменение текущего локального массива.

## 7. Тест-кейсы с неизменяемыми ожиданиями

Тесты хранить на естественном языке с идентификаторами проверок. Для каждого независимого теста использовать собственные параметры и при необходимости собственную подготовительную запись.

### VUESTIC-01 — валидация email

**Предусловие:** форма Add user доступна.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Заполнить Full name и Username валидными параметрами, Email — строкой без @ | Поля содержат введённые значения |
| 2 | Вызвать проверку поля через blur; если Add доступна, попытаться сохранить | Email отклонён: видно сообщение о невалидном адресе; форма остаётся открытой; сохранение не подтверждено |
| 3 | Исправить Email на валидный параметр и снова вызвать проверку | Ошибка email исчезает; при остальных валидных полях Add доступна |
| 4 | Нажать Cancel, при необходимости подтвердить отказ от изменений | Форма закрывается |
| 5 | Выполнить свежий поиск по своему маркеру в Active и Inactive | Запись не создана |

Ожидаемое сообщение по исходникам: `Please enter a valid email address`. До запуска серии подтвердить текст/локализацию на текущем deployment. Отключённая Add при невалидной форме — допустимое заранее описанное поведение; агент не должен пытаться обходить disabled. [V8]

Минимальные check ids: `invalid_email_rejected`, `valid_email_accepted`, `cancel_did_not_create`.

### VUESTIC-02 — создание и чтение

**Основной сценарий переноса знаний.**

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Нажать Add User | Открыт диалог создания |
| 2 | Заполнить Full name, Username, Email и Notes; остальные значения оставить как в параметрах | Прочитанные значения полей соответствуют параметрам |
| 3 | Нажать Add и дождаться результата | Нет подтверждённого отказа сохранения; запись обнаруживается в UI |
| 4 | Выполнить readOwnUserFresh | Найдена ровно одна собственная запись; Full name, Username и Email соответствуют параметрам |
| 5 | Открыть Edit найденной строки | Notes точно соответствует исходным 100 символам; Role = User и Active включён |
| 6 | Закрыть форму без изменений | Таблица снова доступна |

Затем выполнить cleanup. Закрытие модалки или toast без шагов 4–5 не даёт PASS.

Check ids: `form_values_match`, `own_user_created`, `persisted_identity_matches`, `persisted_notes_match`.

Обучаемая процедура может помогать шагам 1–3. Последующие наблюдения остаются общим oracle для всех профилей знаний.

### VUESTIC-03 — изменение Notes

**Подготовка:** создать свою запись в этой же попытке и подтвердить её через свежее чтение.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Открыть Edit своей строки | Идентификаторы и исходные Notes соответствуют подготовленной записи |
| 2 | Заменить Notes на Updated Notes | Поле содержит новое точное значение |
| 3 | Нажать Save, дождаться результата и выполнить свежее чтение | Найдена та же запись |
| 4 | Повторно открыть Edit | Notes соответствует Updated Notes; Full name, Username, Email, Role и Active не изменились |
| 5 | Закрыть форму | Таблица доступна |

Затем cleanup. Сохранение имени неизменным позволяет проверять редактирование без одновременного тестирования перенастройки поиска.

Check ids: `edit_targets_own_user`, `updated_notes_persisted`, `identity_unchanged`.

### VUESTIC-04 — отмена и подтверждение удаления

**Подготовка:** создать свою запись и подтвердить её через свежее чтение.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Нажать Delete user в своей строке | Подтверждение относится к точному имени своей записи |
| 2 | Нажать Cancel и выполнить свежее чтение | Запись остаётся |
| 3 | Повторить Delete user | Снова показано подтверждение нужной записи |
| 4 | Нажать Delete и дождаться результата | Диалог закрыт; результат операции подлежит проверке |
| 5 | Выполнить readOwnUserFresh | Собственная запись отсутствует после завершённых поисков в Active и Inactive |

Check ids: `delete_targets_own_user`, `cancel_preserves_user`, `confirmed_delete_persisted`.

Если после удаления строка исчезла, но после свежего чтения вернулась, проверка удаления не пройдена. Не превращать это в PASS повторным удалением без сохранения первоначального результата.

### Следующие сценарии

После основного цикла можно добавить изменение Active с поиском во вкладке Inactive, Role select, Projects multiselect, аватар и страницу Projects. Это отдельное расширение; они не блокируют готовность первого handoff.

## 8. Три профиля знаний и происхождение навыков

Использовать осмысленные имена профилей, чтобы не смешать их с A/B/C или режимами исполнения из других экспериментов.

| `knowledge_profile` | Доступные знания |
|---|---|
| `fresh` | Пустой каталог навыков |
| `sakai_transfer` | Замороженные общие процедуры, извлечённые только из реальных трасс Sakai |
| `vuestic_learned` | Тот же каталог sakai_transfer плюс навыки из отдельного обучения на Vuestic |

Во всех профилях одинаковы тесты, механизм проверок, модель, браузерные инструменты, политика загрузки навыков и бюджеты. Перед каждой измерительной попыткой создаётся новая Pi-сессия. Cookies и общий профиль браузера сохраняются.

### Перенос из Sakai

Sakai использует PrimeVue; Vuestic — Vuestic UI. Навык создания продукта в Sakai сохраняет свою область применимости. Нельзя просто заменить его scope на Vuestic и считать перенос выполненным.

Explorer должен отдельно извлечь из Sakai-трассы общую процедуру, например:

- распознать открытый диалог создания;
- сопоставить поля текущего теста с наблюдаемыми контролами;
- заполнить значения и прочитать их обратно;
- выполнить подтверждение;
- найти созданную запись и проверить эффект;
- при неоднозначном сохранении сначала проверить наличие результата.

Это примеры ожидаемого уровня абстракции, а не готовый обученный навык. Сам текст навыка должен происходить из реальной трассы.

В переносимую процедуру не должны попасть Vuestic-адреса, подписи, селекторы или действия, полученные из Vuestic-исследования. Специфичные для PrimeVue исполняемые фрагменты остаются ограниченными PrimeVue. Само присутствие Vue 3 на двух сайтах не доказывает переносимость.

### Если Sakai-трассы ещё нет

Использовать существующий успешный артефакт, если он предоставлен. Иначе получить его существующим worker на https://sakai.primevue.org/pages/crud: создать продукт с уникальным именем, описанием и ценой, найти его, проверить поля через повторное открытие формы. Explorer извлекает общую процедуру из этой трассы без наблюдений Vuestic.

Предыдущий handoff и знания разработчика не заменяют обучающую трассу. Если получить её невозможно, продолжить интеграцию Vuestic и доступные тесты; профиль sakai_transfer пометить `UNAVAILABLE` с причиной. Не выдавать вручную написанный навык за накопленный опыт.

Собственное обучение Vuestic при этом доступно: vuestic_learned содержит только местный навык, а отсутствие исходного каталога явно отражается в метаданных. Такой запуск исследует местное обучение; вывод о переносе Sakai по нему делать нельзя.

### Собственное обучение Vuestic

Для vuestic_learned провести отдельную успешную training-попытку VUESTIC-02, затем distillation и две проверки локального кандидата на новых собственных данных в свежих сессиях.

Валидация обязательна для автоматической активации местного навыка. Допускается одна переработка кандидата по результатам провала; общий бюджет ограничен. Во время измерений принятые версии заморожены.

Обе валидационные попытки должны подтверждать применение именно проверяемой версии на предназначенных шагах: загрузка, начало применения и соответствующие действия связаны в трассе с skill id/version. Успех теста после отказа от кандидата или его ошибки с последующим fallback не даёт кандидату успешную валидацию. Для активации нужны полный PASS, подтверждённое применение и отсутствие такого fallback в обеих попытках.

### Применимость и испытание переноса

Общий навык, подтверждённый только в Sakai, может испытываться на Vuestic в профиле sakai_transfer как **кандидат переноса**. Не требуется заранее обучать или подтверждать его на Vuestic: это исказило бы первый опыт.

Метаданные должны различать:

- источник обучения;
- приложение, где процедура уже проверена;
- текущую экспериментальную область применения;
- результат попытки применения на новой странице.

Локаторы разрешаются по текущему UI. Несовпадение предусловий означает отказ от применения и обычное выполнение теста. Успешный fallback может дать PASS тесту, но не считается успешным использованием навыка.

Все процедурные навыки P0 — Markdown. Исполняемые рецепты можно добавить позже как отдельный режим `execution_mode`, одинаково доступный сравниваемым профилям. Не менять одновременно память и набор браузерных возможностей без отдельного отчёта.

## 9. Роли и неизменяемые проверки

### Worker

Получает сценарий, параметры попытки, текущий профиль знаний и бюджеты. Выполняет шаги через browse, проверяет предусловия навыков, записывает действия и наблюдения.

Worker должен:

- работать с собственным объектом, сверяя его идентификаторы;
- учитывать Active/Inactive и фактический поиск;
- при ошибке навыка получать новое наблюдение;
- после timeout сначала выяснять эффект, затем выбирать повтор;
- сохранять все ожидаемые результаты;
- отделять дефект приложения, ошибку собственных действий и недоступность инфраструктуры.

### Explorer

Получает разрешённые для своей фазы трассы, тест и параметры. Создаёт кандидата с происхождением, условиями применимости, процедурой, ограничениями и восстановлением.

Explorer не редактирует сценарии и evaluator, не меняет ожидаемые значения, не записывает активную версию поверх существующей. Новая редакция — новая версия.

Для P0 explorer достаточно чтения трасс; собственная постоянно работающая браузерная сессия не обязательна.

### Evaluator

Предпочтительно использовать существующий механизм. Для перечисленных сценариев достаточно явных проверок наблюдений.

Навык возвращает наблюдения и сведения об эффектах, но не является источником окончательного PASS. Подтверждение одного шага не заменяет остальные; удачные куски разных попыток не собираются в общий успех.

`PASS` требует всех обязательных check ids одной полной попытки.

## 10. Ошибки, восстановление и итог

| Статус теста | Значение |
|---|---|
| `PASS` | Все обязательные ожидания подтверждены |
| `FAIL` | Получено однозначное наблюдение, нарушающее ожидаемый результат |
| `BLOCKED` | Выполнение невозможно из-за доступа, инфраструктуры или отсутствующей возможности |
| `INCONCLUSIVE` | Эффект или доказательства остаются неоднозначными |

В отчёте отдельно записывать причину. Исчезновение чужих строк не является провалом этого теста. Подтверждённое неверное значение собственной записи остаётся нарушением ожидания; нельзя списывать его на публичную среду без доказательств.

### Timeout после Add/Save

1. Сохранить действие и последний известный эффект.
2. Выполнить свежее чтение собственной записи.
3. Если ожидаемые значения присутствуют, продолжить с подтверждённого состояния.
4. Если запись отсутствует, проверить, может ли исходное сохранение ещё завершиться. Само отсутствие записи не разрешает повтор Add: первый запрос может закончиться позже. Выполнить ограниченное ожидание и повторное наблюдение; при сохраняющейся неопределённости завершить INCONCLUSIVE.
5. Повтор с теми же параметрами разрешён только при подтверждённом завершении первой операции без нужного эффекта либо доказанном отсутствии её отправки. Транспортный timeout сам по себе таким подтверждением не является. При дубликатах, конфликте значений или неуспешном чтении получить дополнительное наблюдение либо завершить INCONCLUSIVE.
6. Подтверждённое нарушение check id сохраняется, даже если последующее восстановление удалось.

### Timeout после Delete

Выполнить свежее чтение. Подтверждённое отсутствие означает, что нужный эффект наблюдён. Наличие записи после успешно завершённого чтения означает, что удаление ещё не подтверждено; повтор допускается только после записи результата первой операции и в рамках бюджета.

Если удаление входит в основной тест и проверка уже однозначно провалилась, recovery не переписывает её в PASS. Новый полный тест получает новый attempt_id.

### Защита от циклов

Сохранить текущий LLM-cap. Дополнительно учитывать число браузерных действий и elapsed time. Известная последовательность внутри одного `execute` тоже потребляет этот бюджет.

При исчерпании бюджета незавершённые проверки не считаются успешными. Постоянный повтор одного и того же действия без нового наблюдения должен останавливаться.

## 11. Трассы и небольшой эксперимент

### Артефакты

```text
artifacts/vuestic/<run_id>/
  environment.json
  config.json
  phase-manifest.json
  attempts/<attempt_id>/
    parameters.json
    events.jsonl
    result.json
    evidence/
  skills/
    sakai-transfer/<version>/
    vuestic-create-user/<version>/
  pending-cleanup.json
  comparison.json
  report.md
```

Использовать существующие каталоги проекта, если их назначение совпадает. Отдельная БД не требуется.

### Минимальные поля результата

```json
{
  "schema_version": 1,
  "case_id": "VUESTIC-02",
  "knowledge_profile": "sakai_transfer",
  "execution_mode": "procedural",
  "status": "INCONCLUSIVE",
  "checks": [],
  "skill_usage": {
    "loaded": false,
    "applicable": null,
    "used": false,
    "fallback": false,
    "version": null
  },
  "metrics": {
    "llm_calls": 0,
    "input_tokens": null,
    "output_tokens": null,
    "mcp_calls": 0,
    "browser_actions": 0,
    "elapsed_ms": 0
  },
  "cleanup_status": "not_needed"
}
```

Это пример формы данных, не результат прогона. Реальные run_id, attempt_id, параметры, версии и evidence добавляются из харнесса. Неизвестные usage-метрики записываются как null, не как нулевая стоимость.

JSONL должен содержать начало/конец попытки, LLM-вызовы, загрузку и применение навыка, инструментальные действия, сырые MCP-ответы, наблюдения, проверки, retries, fallback и cleanup.

Результат MCP не всегда является готовым JSON; сохранять сырой ответ, проверять `isError`, явно обрабатывать неизвестный формат. Snapshot refs и tab id не включать в долговечный навык. Если `execute` содержит несколько действий, нужны внутренние события или checkpoints; после прерывания неизвестные подшаги так и остаются неизвестными. [B2]

### Минимальная серия

Для первого отчёта достаточно:

1. Диагностического smoke.
2. Готового source-only навыка Sakai или честно зафиксированного UNAVAILABLE.
3. Одной измерительной попытки VUESTIC-02 в fresh.
4. Одной измерительной попытки VUESTIC-02 в sakai_transfer.
5. Отдельного обучения Vuestic и двух валидаций местного кандидата.
6. Одной измерительной попытки VUESTIC-02 в vuestic_learned.
7. VUESTIC-01 в fresh и VUESTIC-03/04 в vuestic_learned как проверок остальной интеграции.

Если местный навык не прошёл валидацию, не запускать под его именем обычный baseline; профиль vuestic_learned пометить недоступным с причиной. Доступные сценарии можно проверить в fresh.

Для более содержательного наблюдения повторить VUESTIC-02 несколько раз в каждом профиле, чередуя порядок, и при необходимости выполнить остальные тесты во всех профилях. Одинаковый снимок backend не требуется.

### Что показать в отчёте

- Все попытки, статус и обязательные check ids.
- LLM-вызовы, токены при доступности usage, время, MCP-вызовы и внутренние браузерные действия.
- Повторы, восстановления, fallback и остатки cleanup.
- Был ли навык загружен, применим и фактически использован.
- Какие действия удалось повторить из опыта Sakai и какие пришлось выяснять заново.
- Стоимость обучения и валидации отдельно от измерительных запусков.
- Наблюдаемые задержки/ошибки среды отдельно от времени LLM, если это доступно.

Один MCP execute с несколькими действиями — один MCP-вызов, но несколько браузерных действий. Стоимость подготовки своей записи включается в полный тест; cleanup и собственно проверяемые шаги дополнительно показываются отдельными фазами.

Сравнение скорости успешных выполнений допустимо, но рядом должны оставаться неудачные попытки и их затраты. Для малого числа запусков использовать формулировки «в этих попытках наблюдалось…». Не объявлять перенос на всю Vue-экосистему или доказанное ускорение по одному удачному проходу.

### Узкие проверки кода

Использовать существующий тестовый каркас. Достаточно проверить существенные риски:

- read_failed не преобразуется в not_found;
- отсутствие только в Active не подтверждает удаление, если запись найдена в Inactive;
- delete после HTTP-ошибки и исчезновения локальной строки не получает PASS без свежего чтения;
- после timeout Add параметры сохраняются; отсутствие записи при потенциально незавершённом первом запросе не разрешает повторное создание;
- sakai_transfer не загружает навыки с Vuestic provenance;
- неполный набор check ids и кандидат, чьи валидации прошли через fallback, не считаются успешными;
- cleanup отказывается менять неоднозначно идентифицированную запись.

Имитации ответов в этих проверках тестируют логику харнесса и не заменяют реальные браузерные прогоны.

## 13. Результат и критерии готовности

После реализации должны остаться: код интеграции, четыре теста, промпты worker/explorer, команды запуска, конфигурация без секретов, реальные трассы, версии навыков с происхождением и отчёт.

- [ ] Основной URL — текущее публичное /users.
- [ ] Нет обязательного backend reset, локального deployment или отката на v4.0.0.
- [ ] Использованы текущие Pi, модель и Rust browse.
- [ ] Свои записи идентифицируются точными параметрами.
- [ ] Create/Update/Delete проверяются новым чтением через UI.
- [ ] Все четыре сценария реализованы; фактически исполненные и заблокированные случаи различимы.
- [ ] fresh, sakai_transfer и vuestic_learned имеют явные источники знаний.
- [ ] Отсутствие исходной трассы или неуспешная валидация не маскируются.
- [ ] Навыки не ослабляют oracle и не публикуются через человеческий gate.
- [ ] Отчёт различает успех теста, использование навыка и fallback.
- [ ] Затраты, ошибки среды и cleanup отражены.
- [ ] Граница доказанного переноса соответствует реальным попыткам.

Готовность интеграционного кода и подтверждение экспериментальной гипотезы — отдельные результаты. Если среда не позволила выполнить CRUD, это должно быть видно в итоговом отчёте. Если навыки не улучшили результат, такой вывод сохраняется.
