# Handoff: первый эксперимент с обучаемым QA-агентом на Sakai Vue

Дата: 22 ноября 2026 года. Версия: 1.0.  
Адресат: код-агент, который будет реализовывать прототип в локальном окружении заказчика.  
Статус: задание на реализацию. Исходники изучены; браузерный прогон и сам прототип ещё не выполнены.

## 0. Инструкция код-агенту

Реализуй локальный воспроизводимый эксперимент: QA worker выполняет тест Sakai CRUD без накопленных знаний; отдельная сессия explorer извлекает из успешной трассы один навык; после автоматической проверки свежий worker использует этот навык на новых данных. Сравни корректность, LLM-вызовы, токены и время.

Начни с изучения существующего репозитория харнесса, его инструкций, механизма запуска Pi и реальных схем инструментов opencode browse. Затем выполняй этапы из раздела 12. Используй существующие интерфейсы и зависимости, где они подходят. Пути модулей ниже — предлагаемая структура, а не утверждение о содержимом репозитория.

Достаточно закончить обязательный этап P0. Его результат — работающий цикл «исполнение → извлечение навыка → автоматическая проверка → повторное исполнение» и честный отчёт. Ускорение нужно измерить; отсутствие ускорения тоже является допустимым результатом эксперимента.

Для выполнения задания не требуется история переписки. Этот файл содержит требования, ограничения, сценарии, правила сравнения и источники. Если в рабочем каталоге нет исходников харнесса или доступа к установленному browse, точно укажи недостающий ресурс; не подменяй интеграцию демонстрацией на другом браузерном стеке.

## 1. Контекст и фиксированные решения

Конечная система предназначена для примерно 10 000 подробных тестов на естественном языке по примерно 10 корпоративным DevOps/MLOps/DataOps-платформам. Типичные операции: формы и валидация, таблицы, поиск, фильтры, сортировка, пагинация, меню, вкладки, модальные окна, календари, загрузка файлов, CRUD и подтверждения действий. Sakai нужен как доступный учебный стенд до появления корпоративного доступа.

| Область | Решение для прототипа |
|---|---|
| Харнесс | Существующий кастомный харнесс на Pi |
| Модель | Текущая настроенная open-source модель; провайдер и точный идентификатор сохраняются в отчёте |
| Браузер | Chrome через opencode browse: существующий Rust runtime, MCP |
| Playwright | Не устанавливать, не возвращать в зависимости и не использовать как обходной путь |
| Роли | Worker и explorer — отдельные Pi-сессии с разными промптами и доступами |
| Автономность | Извлечение, проверка и активация навыка происходят автоматически, без утверждения человеком |
| Локальность | Трассы, навыки, конфигурация и отчёты хранятся локально у тестировщика |
| Параллельность P0 | Один worker, одна выделенная вкладка, последовательные попытки; explorer запускается после обучающей попытки |
| Браузерный профиль | Используется существующий профиль. Общие cookies между вкладками приемлемы по условиям заказчика |
| Ограничения | Сохраняется лимит LLM-вызовов; дополнительно учитываются время и число браузерных действий |
| Критерий корректности | Все заданные ожидаемые результаты проверяются независимо от навыка |

Локальное хранение не означает, что настроенная модель обязательно работает на самом компьютере. Способ обращения к модели сохраняется таким, как он устроен в существующем харнессе.

Для P0 не нужны постоянный фоновый explorer, многоплатформенный registry, векторная БД, новый планировщик, общий язык автоматизации или полноценный безоконный Chrome. Фоновая Pi-сессия и отдельная вкладка существующего Chrome достаточны.

## 2. Почему Sakai и что именно мы проверяем

Основной адрес: **https://sakai.primevue.org/pages/crud**.  
Исходники: **https://github.com/primefaces/sakai-vue**.  
Зафиксированная для исследования ревизия: **`ec6b6ef53ad4fa7f2861277f50f2d9e236c40372`**. [S1–S5]

Sakai — Vue-приложение с компонентами PrimeVue. В `package.json` этой ревизии указаны диапазоны `vue: ^3.4.34` и `primevue: ^4.5.4`; это требования зависимостей, а не доказательство точных версий установленного публичного демо. [S2]

CRUD-страница подходит по форме взаимодействия: таблица записей, поиск, создание и редактирование через диалог, числовые поля, выпадающий список, радиокнопки, подтверждение удаления и уведомления. [S3]

**Гипотеза эксперимента:** повторное использование процедуры, извлечённой из успешного взаимодействия с UI, уменьшает затраты следующего выполнения при сохранении тех же проверок.

Первый навык имеет область применения **Sakai / PrimeVue / создание продукта**. Сам факт использования Vue не делает процедуру универсальной для всех Vue-приложений: библиотека компонентов, разметка, локализация и логика приложения тоже влияют на взаимодействие. Перенос на другую страницу или платформу потребует отдельного опыта.

### Граница проверки на момент подготовки handoff

Подтверждены чтением исходников: стек, маршрут, структура CRUD-страницы, локальная модель данных и правила сохранения. Публичный адрес отвечал на HTTP-запрос при исследовании. Полноценного браузерного smoke test не было; доступность всех действий, фактические DOM/AX-представления и соответствие развёрнутого демо указанной ревизии пока не подтверждены.

Первое задание реализации — проверить живой интерфейс через установленный browse и сохранить наблюдения.

## 3. Подтверждённые особенности CRUD-страницы

### 3.1. Данные и сброс

При монтировании страницы `ProductService.getProducts()` возвращает встроенный массив. Создание добавляет элемент в локальный массив, редактирование заменяет элемент, удаление фильтрует массив. В исследованном коде эти операции не обращаются к серверному CRUD API. [S3, S4]

Следствия для стенда:

- Полная перезагрузка или повторное монтирование страницы возвращают исходные демоданные. Это нужно подтвердить первым браузерным прогоном.
- Внутри зависимой последовательности create → edit → delete перезагружать страницу нельзя.
- Перед независимой попыткой выполняется явный сброс страницы и проверяется исходное состояние.
- У разных вкладок ожидается независимое состояние компонента; это вывод из кода, а не результат проведённого многовкладочного теста.
- Эксперимент проверяет UI-взаимодействие, обучение процедурам и проверки результата. Персистентность, права доступа и работа корпоративного backend здесь не моделируются.

### 3.2. Интерфейс и ловушки для агента

| Элемент | Известное поведение и требование |
|---|---|
| Заголовок страницы | `Manage Products` |
| Создание | Кнопка `New` открывает диалог `Product Details` |
| Поиск | Поле с placeholder `Search...`; глобальная фильтрация по подстроке |
| Name | Непустое имя после trim — условие сохранения; при пустом имени показывается `Name is required.` |
| Description | Текстовое поле. Наличие `required` в шаблоне не означает, что обработчик сохранения реально запрещает пустое описание |
| Inventory Status | Метки `INSTOCK`, `LOWSTOCK`, `OUTOFSTOCK`; значения выбранных опций в коде — lowercase |
| Category | Радиокнопки `Accessories`, `Clothing`, `Electronics`, `Fitness` |
| Price | Числовое поле с валютным форматированием USD, локаль en-US |
| Quantity | Числовое поле |
| Кнопки формы | `Cancel` и `Save` |
| Действия строки | Редактирование и удаление — кнопки с иконками карандаша и корзины; текстовые accessible names нельзя предполагать |
| Удаление | Диалог `Confirm`, имя удаляемого продукта в тексте, кнопки `No` и `Yes` |
| Таблица | Пагинация, выбор размера страницы, сортируемые колонки и выбор нескольких записей |

Основание таблицы — исходник `Crud.vue`. [S3]

Необходимо учесть:

1. Обработчик `saveProduct` явно проверяет только имя. Не вводить неподтверждённые ожидания обязательности описания, категории, цены, количества или статуса.
2. Кнопку редактирования/удаления находить внутри строки с точным именем созданной записи. Поиск глобальной кнопки с предположительным названием `Edit` или фиксированного номера строки ненадёжен.
3. При проверке цены сравнивать числовое значение, например в центах; исходный ввод и валютное отображение могут различаться.
4. Описание не видно в таблице: для его проверки нужно открыть созданную запись и прочитать текущее значение поля.
5. Нельзя считать snapshot достаточным для чтения значений, если установленный browse их не включает. Допустимо дополнить наблюдение чтением DOM-свойств поля через поддерживаемый браузерный API.
6. В коде смешаны uppercase статусы исходных данных/значения по умолчанию и lowercase значения выбранных опций. В P0 статус не включать в обязательный oracle. Если проверка статуса добавляется, сначала явно определить ожидаемое представление и сохранить обнаруженное расхождение; не нормализовать его молча ради прохождения.
7. Если при активном поиске переименовать запись, старый фильтр может скрыть её. Обязательный тест редактирования меняет цену, сохраняя имя.

Ни одну из этих особенностей нельзя использовать для обхода UI: не вызывать обработчики Vue напрямую, не менять reactive state, не записывать данные в фикстуры вместо пользовательских действий.

## 4. Подготовка стенда и первый smoke test

### 4.1. Выбор адреса

Для первого ручного запуска харнесса использовать публичный URL. Для воспроизводимой серии измерений предпочтителен локальный Sakai на зафиксированном commit, если необходимые зависимости доступны.

Пример подготовки отдельной копии стенда:

```bash
git clone https://github.com/primefaces/sakai-vue.git sakai-vue-qa-fixture
cd sakai-vue-qa-fixture
git checkout --detach ec6b6ef53ad4fa7f2861277f50f2d9e236c40372
npm ci
npm run dev -- --host 127.0.0.1 --port 5173
```

Локальный URL: `http://127.0.0.1:5173/pages/crud`. Скрипт `dev` в исследованном package запускает Vite. [S2]

До запуска проверить доступный Node/npm и lockfile. При несовместимости зависимостей зафиксировать ошибку и выбрать совместимое окружение, не обновляя произвольно зависимости стенда. Не менять исходники Sakai для облегчения прохождения тестов. Публичный и локальный адреса не смешивать внутри одной серии A/B.

### 4.2. Что выяснить о browse

Исследованный browse — Rust relay, Chromium extension/CDP и выполнение JavaScript в QuickJS. Набор MCP tools зависит от конфигурации и клиента; нельзя исходить из наличия определённого метода только по названию проекта. [B1–B4]

Код-агент должен сохранить в `environment.json`:

- версию/commit установленного browse, если доступен;
- фактический ответ MCP `tools/list` и используемые схемы;
- способ подключения из существующего Pi-харнесса;
- доступность отдельных действий либо `execute` и ограничения его среды;
- идентификатор выделенной вкладки;
- версию Chrome, viewport и целевой URL;
- идентификатор модели и фактические настройки генерации.

Для другого MCP-клиента набор инструментов может отличаться от OpenCode. В исследованной реализации доступен выбор `plain|execute|all` через `OPENCODE_BROWSER_TOOLS`. Это настройка relay; не менять её и не перезапускать общий браузер без необходимости. Сначала использовать уже доступный интерфейс. [B1, B4]

Если интерфейс browse содержит совместимые с привычными браузерными библиотеками названия, это не означает наличие полной Playwright API или Node.js внутри `execute`. Использовать только подтверждённые возможности текущей версии. [B3]

### 4.3. Обязательный smoke test

В выделенной вкладке:

1. Открыть CRUD URL, дождаться таблицы, сохранить наблюдение.
2. Нажать `New`, убедиться, что открыт `Product Details`.
3. Сохранить с пустым именем; проверить сообщение `Name is required.` и сохранение открытого диалога.
4. Ввести уникальное имя, описание и цену; сохранить.
5. Найти запись по имени, проверить цену в таблице.
6. Открыть её редактирование, проверить описание и цену через UI.
7. Закрыть диалог, перезагрузить страницу; убедиться, что созданной записи больше нет и таблица снова готова.

Это диагностика стенда и интеграции, не обучение кандидата и не измерение эффективности. Трассу smoke test хранить отдельно и не передавать в baseline-сессии.

Если живой сайт отличается от исходников, сохранить DOM/AX-наблюдение и скриншот проблемного места. Можно перейти на локальную закреплённую ревизию и повторить smoke test. Нельзя молча изменять ожидаемые результаты тестов, чтобы скрыть различие.

## 5. Тестовые данные и неизменяемые ожидаемые результаты

Тесты хранить как обычные пошаговые Markdown-сценарии с отдельными идентификаторами проверок. Это соответствует исходному формату корпоративных тестов. Не требуется сначала строить универсальный парсер естественного языка.

Данные генерируются харнессом из `seed` до запуска попытки. Конкретные значения передаются worker как параметры, а ожидаемые значения — механизму проверки. Рекомендуемые правила P0:

| Параметр | Правило |
|---|---|
| `name` | Уникальное имя с префиксом `qa_`, идентификатором серии и номером пары |
| `description` | Ровно 100 ASCII букв/цифр, воспроизводимых по seed |
| `price_cents` | Положительное целое число центов, выбранное генератором в явно заданном диапазоне |
| `updated_price_cents` | Другое положительное значение, отличающееся от первоначального |
| `quantity` | Для расширенного сценария: небольшое положительное целое |
| `category/status` | Для расширенного сценария: правило выбора конкретной/первой/последней опции, зафиксированное до попытки |

Генератор должен один раз материализовать данные попытки. Повтор действия после сбоя использует те же значения. Нельзя создавать новое имя в каждой итерации восстановления и терять связь с исходной записью.

В A/B-паре параметры одинаковы; между парами меняется seed. Сброс страницы позволяет безопасно повторить имя внутри пары. Обучение, валидация навыка и измерения используют разные наборы seed.

### Общие правила проверки

- Строка определяется точным совпадением имени внутри найденных результатов, а не только наличием текста где-либо на странице.
- Для положительного результата требуется ровно одна соответствующая строка.
- Уведомление об успехе — дополнительное наблюдение; оно не заменяет проверку записи.
- Проверка цены сравнивает числовое значение, проверка описания — точное содержимое.
- Неполученное или неоднозначное наблюдение не является успешной проверкой.
- Основной runtime может использовать существующий evaluator. Для четырёх сценариев ниже предпочтительны простые явные проверки наблюдений, отделённые от навыка.
- Код evaluator и список проверок фиксируются до обучения. Explorer не может их редактировать.

## 6. Обязательные тест-кейсы P0

Каждый тест независим, начинается с подтверждённого сброса и сам создаёт нужную ему запись. Вложенные шаги подготовки остаются частью полной трассы. Сброс между попытками выполняет оркестратор; внутри теста reload запрещён.

### SAKAI-01 — валидация пустого имени

**Предусловие:** CRUD-таблица готова, поиск очищен.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Нажать `New` | Открыт `Product Details` |
| 2 | Оставить имя пустым и нажать `Save` | Диалог остаётся открытым; видно `Name is required.` |
| 3 | Нажать `Cancel` | Диалог закрыт; снова доступна таблица |

Это отдельный негативный сценарий. Использовать навык создания с непустым именем здесь неприменимо.

### SAKAI-02 — создание, поиск и чтение записи

**Параметры:** `name`, `description`, `price_cents`.  
**Назначение:** основной сценарий обучения и измерения.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Открыть `New` | Открыт диалог создания |
| 2 | Заполнить имя, описание и цену | Прочитанные значения полей соответствуют параметрам |
| 3 | Нажать `Save` | Диалог закрыт |
| 4 | Ввести точное имя в поиск | Найдена ровно одна строка с этим именем; цена соответствует параметру |
| 5 | Открыть редактирование найденной строки | Открыт диалог этой записи; имя, описание и цена соответствуют параметрам |
| 6 | Нажать `Cancel` | Диалог закрыт; запись остаётся в результатах поиска |

Описание проверяется на шаге 5 по текущему значению поля. Появление записи в таблице само по себе не доказывает, что всё содержимое формы сохранено.

Первый обучаемый навык охватывает шаги 1–3: открытие, заполнение и сохранение. Шаги 4–6 остаются общей независимой проверкой для обоих режимов. Проверки значений на шаге 2 выполняются в обоих режимах и не исчезают при использовании навыка.

### SAKAI-03 — изменение цены

**Подготовка:** в этой же попытке создать собственную запись с её параметрами и проверить успешное создание.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Найти свою запись и открыть редактирование | Диалог содержит её имя и исходную цену |
| 2 | Изменить только цену | Поле содержит `updated_price_cents` |
| 3 | Сохранить | Диалог закрыт; соответствующая строка показывает новую цену |
| 4 | Повторно открыть редактирование | Новая цена сохранена; имя и описание не изменились |
| 5 | Закрыть диалог | Таблица доступна |

Подготовка может использовать активный навык в treatment-режиме. Её стоимость отражается отдельно, а полный итог теста включает все действия.

### SAKAI-04 — отмена и подтверждение удаления

**Подготовка:** в этой же попытке создать собственную запись и найти её по имени.

| Шаг | Действие | Ожидаемый результат |
|---|---|---|
| 1 | Нажать удаление в своей строке | Открыт `Confirm`; текст относится к нужному имени |
| 2 | Нажать `No` | Диалог закрыт; запись по-прежнему присутствует |
| 3 | Ещё раз нажать удаление | Снова открыто подтверждение для нужной записи |
| 4 | Нажать `Yes` | Диалог закрыт |
| 5 | Проверить результаты поиска по имени | Соответствующих строк нет; наблюдение получено после завершения обновления UI |

Удалять другие записи ради очистки не требуется: сброс между попытками возвращает исходное состояние.

### Расширение после P0

Отдельными тестами можно добавить Quantity, Category, Inventory Status, сортировку, пагинацию, множественный выбор, массовое удаление и Export. Календари и загрузка файлов потребуют других страниц стенда. Эти сценарии не являются условием готовности первого эксперимента.

## 7. Архитектура минимального цикла

Оркестратор последовательно запускает следующие фазы:

1. **Обучающая попытка.** Свежий worker без накопленных навыков выполняет SAKAI-02 на training seed.
2. **Извлечение.** Отдельная explorer-сессия читает успешную трассу и формирует один кандидат `sakai-create-product`.
3. **Автоматическая валидация.** Свежие worker-сессии проверяют кандидата на двух других seed с теми же ожидаемыми результатами.
4. **Активация.** Кандидат становится активным только после прохождения проверок и проверки полноты артефактов.
5. **Измерение.** Свежие сессии выполняют режим A без навыка и режим B с замороженной активной версией.
6. **Отчёт.** Оркестратор сопоставляет проверки, время, LLM-вызовы, токены и затраты обучения.

### Режим P0: процедурный Markdown-навык

Обязательная первая версия навыка — компактный Markdown: условия применимости, параметры, последовательность, наблюдения и восстановление. Worker подгружает его через существующий механизм навыков либо через небольшой локальный loader.

Навык может уменьшить поиск подходящих действий, число ошибочных попыток и размышления. Сам по себе Markdown не гарантирует сокращения браузерных вызовов или LLM-циклов; это нужно показать измерениями.

### Режим P1: исполняемая процедура

После готовности P0 можно добавить параметризованный код/рецепт для открывания и заполнения формы. Он выполняет известные действия без нового LLM-вызова между ними через текущие инструменты browse.

Выбрать один поддерживаемый способ исполнения:

- последовательное выполнение существующих браузерных команд харнессом;
- либо `execute` установленного browse с наблюдаемыми подшагами.

Не требуется реализовывать оба backend или универсальный DSL. До принятия процедуры должны сохраняться те же промежуточные проверки, параметры, ограничения времени и частичные эффекты.

Добавление такой процедуры — отдельный эксперимент C. Сравнение A/B измеряет пользу текстового навыка; сравнение B/C дополнительно показывает эффект исполнения готовой последовательности. Не объединять результаты разных режимов в один показатель «память ускорила агента».

## 8. Роли, инструменты и граница знаний

### Worker

В системном промпте зафиксировать:

- выполняй выданный тест последовательно, сохраняя все его ожидаемые результаты;
- используй параметры попытки, не придумывай новые значения без предусмотренного правилом основания;
- перед применением навыка проверь URL/страницу, предусловия и соответствие задаче;
- при несовпадении интерфейса останови применение навыка и получи новое наблюдение;
- после действия проверь требуемый эффект; успех вызова инструмента не равен успеху теста;
- после таймаута потенциально завершившегося Save сначала проверь наличие записи;
- не изменяй тесты, evaluator или активные навыки;
- не вызывай Vue-обработчики и не обходи UI записью во внутреннее состояние.

Инструменты worker: текущий browse, чтение доступных навыков, запись событий через харнесс. Интерфейс доступа к навыкам одинаковый в A и B; в A каталог пуст, в B доступна одна замороженная версия. Не подмешивать в B дополнительные браузерные возможности.

### Explorer

Вход: завершённая успешная обучающая трасса, исходный тест, схема параметров, документированные возможности текущего browse.

Выход: новый кандидат навыка и метаданные происхождения.

Промпт explorer должен требовать:

- описывать только процедуру, подтверждённую трассой;
- отделять значения конкретной попытки от параметров;
- сохранять условия применимости и известные точки отказа;
- избегать tab id, snapshot refs, случайных product id и конкретных обучающих значений;
- не переносить в навык итоговый `PASS` как доказательство будущего успеха;
- не менять ожидаемые результаты и не добавлять исключения для обхода неудачных проверок.

В P0 explorer не требуется собственная браузерная вкладка: кандидат проверяется обычным worker в новых сессиях. Постоянный explorer, самостоятельно исследующий сайт, — дальнейшее расширение.

### Чтение исходников и честность опыта

Код-агент может изучать Sakai для развёртывания и понимания ограничений стенда. Runtime worker и explorer получают тесты, браузерные наблюдения и трассы. Не передавать им весь этот handoff как системный промпт: он содержит сведения из исходников.

Запрещено вручную встроить в кандидата найденные в исходниках селекторы или готовую реализацию создания и затем объявить это обучением. Runtime-селекторы и процедуры извлекаются из наблюдаемого интерфейса и успешного исполнения. Явные проверки для evaluator допускаются, но evaluator одинаков в обоих режимах и не служит скрытым источником готовой процедуры для worker.

## 9. Контракт навыка и автоматическая активация

Для P0 достаточно локальных версионированных файлов. Если у харнесса уже есть формат навыков, использовать его; иначе взять следующий минимальный контракт.

### SKILL.md

Обязательные разделы:

1. Назначение и область применения.
2. Как распознать подходящую страницу и исходное состояние.
3. Входные параметры.
4. Последовательность действий, выведенная из трассы.
5. Наблюдения, необходимые между действиями.
6. Восстановление после частичного выполнения.
7. Известные ограничения.

Рекомендуемый размер тела — до 800 слов. Если полезный навык короче, не дополнять его ради объёма. Фиксированные наблюдаемые подписи элементов допустимы; фиксированные данные обучающей записи и эфемерные ссылки на элементы — нет.

### manifest.json

Пример структуры метаданных; значения `status` и списки попыток ниже иллюстративные:

```json
{
  "id": "sakai-create-product",
  "version": 1,
  "status": "candidate",
  "scope": {
    "app": "sakai-vue",
    "component_library": "primevue",
    "route": "/pages/crud",
    "operation": "create-product"
  },
  "parameters": ["name", "description", "price_cents"],
  "source_attempt_ids": [],
  "validation_attempt_ids": [],
  "content_sha256": null,
  "browser_capabilities_sha256": null
}
```

В реальном артефакте источник, digest и записи валидации должны быть заполнены. Точный URL и версии окружения хранятся в run manifest; у навыка должна быть проверка соответствия фактической странице.

### Правила продвижения

Кандидат автоматически получает `active`, когда:

- существует полностью успешная исходная трасса;
- соблюдены формат, параметры и запрет эфемерных ссылок;
- оба валидационных прогона на других данных завершились `PASS` по неизменённым проверкам;
- worker действительно загрузил кандидата, а не успешно выполнил весь тест после отказа от него;
- отсутствуют ошибки рецепта, скрытые исключения и неполные обязательные наблюдения;
- сохранены версии текста навыка, тестов и инструментария.

При провале кандидат остаётся неактивным. Допускается одна автоматическая переработка по трассе провала и новая полная валидация. Число попыток и LLM-бюджеты конфигурируемы; бесконечного цикла улучшения быть не должно.

Во время измерений активный навык заморожен. Изменение создаёт новую версию и новую серию. Человек для продвижения кандидата не нужен.

## 10. Трассы, проверки, ошибки и частичные эффекты

### Минимальные артефакты

```text
artifacts/sakai/<run_id>/
  environment.json
  config.json
  cases.json
  phase-manifest.json
  attempts/<attempt_id>/
    parameters.json
    events.jsonl
    result.json
    evidence/
  skills/sakai-create-product/v1/
    SKILL.md
    manifest.json
    validation.json
  comparison.json
  report.md
```

В существующем проекте расположение может быть другим. Важно, чтобы по отчёту можно было восстановить параметры, действия, проверки и конкретную версию навыка.

### События JSONL

Минимальные поля: `schema_version`, `run_id`, `attempt_id`, `case_id`, `phase`, `mode`, монотонный `seq`, время, тип события.

Типы событий:

- начало/конец попытки;
- LLM-вызов и его usage, если провайдер возвращает usage;
- загрузка/применение/отказ от навыка;
- начало браузерного действия, его аргументы, сырой MCP-ответ и длительность;
- наблюдение;
- проверка с `check_id`, ожидаемым значением, наблюдаемым значением, verdict и ссылкой на evidence;
- ошибка, повтор, fallback и восстановление;
- итог.

Сохранять достаточно сырых данных, чтобы проверить нормализацию результата инструмента. MCP-ответ может содержать текст и `isError`; не считать любой непустой ответ успешным и не предполагать наличие JSON заранее. Неизвестный формат должен давать явный unknown/ошибку адаптера. [B2, B3]

`Snapshot ref` и другие ссылки на элементы действуют в контексте текущей вкладки/документа. Не сохранять их как долговечные локаторы навыка. [B2]

Если используется один `execute`, внешние hooks видят один вызов. Внутренние действия и проверки должны дополнительно появляться в трассе. При timeout и отсутствии финального пакета сохранить известную границу выполнения; недостающие подшаги пометить как неизвестные и выполнить наблюдение восстановления. Итоговой строки `success` недостаточно. [B3]

### Итоговые статусы

| Статус | Значение |
|---|---|
| `PASS` | Все обязательные проверки одной полной попытки подтверждены |
| `FAIL` | Получено однозначное UI-наблюдение, нарушающее ожидаемый результат |
| `BLOCKED` | Выполнение невозможно из-за инфраструктуры, доступа или отсутствующих возможностей |
| `INCONCLUSIVE` | Действия могли произойти, но доказательств для полного результата недостаточно |

Дополнительно сохранять причину: application mismatch, agent action error, timeout, tool error, missing evidence и т. п. Не объявлять каждую ошибку агента дефектом Sakai.

Если лимит исчерпан до обязательных проверок, результат не `PASS`. Нельзя собирать успех из удачных фрагментов нескольких неполных попыток.

### Восстановление

- Перед повтором `Save` после timeout найти запись по тому же имени и проверить её поля.
- Если запись уже соответствует параметрам, продолжить с подтверждённого состояния.
- Если эффект неоднозначен, получить дополнительное наблюдение либо завершить попытку `INCONCLUSIVE`.
- Если найдены дубликаты, зафиксировать проблему; не скрывать её удалением лишней записи перед итоговой проверкой.
- После сбоя заполнения формы прочитать текущие значения и исправить только необходимое.
- Любой новый полный запуск получает отдельный `attempt_id`, собственный reset и полный набор проверок.

## 11. Протокол сравнения

### Что одинаково в A и B

| Параметр | Требование |
|---|---|
| Модель и провайдер | Один идентификатор, одинаковые фактические настройки |
| Тесты и evaluator | Одинаковый текст, check ids и версии |
| Browser tools | Одинаковые схемы и разрешённые операции |
| Данные | Одинаковые внутри пары; разные между парами |
| Состояние | Подтверждённый reset перед каждой попыткой |
| Агентная память | Свежая Pi-сессия; нет истории предыдущих запусков |
| Лимиты | Одинаковые бюджеты и правила повторов |
| Каталог навыков | A: пустой; B: одна замороженная прошедшая валидацию версия |
| Очередность | A→B для одной пары, B→A для следующей |

Температуру и seed модели фиксировать, если провайдер это поддерживает. Не считать отсутствие такой настройки ошибкой стенда; записать ограничение. При доступном prompt cache сохранять cache usage и не приписывать весь выигрыш времени навыку.

### Объём первого эксперимента

1. Smoke test интеграции — отдельно.
2. Одна успешная обучающая попытка SAKAI-02; неудачные попытки и их стоимость также сохраняются.
3. Два валидационных запуска SAKAI-02 на новых seed.
4. Основное сравнение SAKAI-02: пять пар A/B на пяти других seed.
5. Остальные три сценария: по одной паре A/B для проверки сохранения поведения.

Для быстрой проверки команды допустим режим с одной измерительной парой. Он должен быть явно помечен как smoke, а не полноценное сравнение эффективности. Пять пар — тоже небольшой пилот; не заявлять по нему универсальный или статистически надёжный эффект для всех корпоративных тестов.

### Метрики

На каждую попытку:

- статус и число подтверждённых обязательных проверок;
- LLM-вызовы, входные/выходные токены, если доступны;
- elapsed time всей попытки;
- число верхнеуровневых MCP-вызовов;
- число фактических браузерных действий внутри них;
- число ошибок, повторов и восстановлений;
- факт загрузки, применимости, использования и отказа от навыка;
- стоимость подготовки записи и стоимость основных проверяемых действий.

Время reset и запуска сессии учитывать отдельно и дополнительно показывать общее время пользовательского запуска. Временные границы должны быть одинаковы в A и B. Один `execute` с десятью действиями — один MCP-вызов и десять действий, а не одно действие.

В отчёте показать все попытки, долю `PASS` и парные изменения LLM-вызовов/времени. Для сравнения скорости успешного выполнения отдельно выделить пары, где оба режима `PASS`, и явно указать их количество. Провалы и затраты на повторы остаются в общем итоге.

Обучение, извлечение, неудачные кандидаты и валидация показываются отдельной стоимостью. Если средняя экономия одного успешного повторения положительна, можно оценить порог окупаемости как «стоимость обучения и проверки / экономия на повторении» в одной единице измерения. При неположительной экономии порог по этому измерению не достигнут.

Успешный fallback после неприменимого навыка может дать `PASS` самому тесту, но не является успешным применением навыка. Это отдельный флаг в результатах.

## 12. План реализации для код-агента

### Задача 1. Проверить существующую интеграцию

Прочитать инструкции репозитория и найти точки запуска сессий Pi, подключения MCP, hooks, лимитов и сохранения результатов. Получить реальные схемы browse. Выполнить smoke test из раздела 4.

**Готово, когда:** `environment.json` и smoke-трасса существуют; создание, чтение и reset подтверждены; выявленные несовпадения описаны.

### Задача 2. Добавить сценарии и параметры

В существующей структуре тестов создать четыре Markdown-сценария, генератор параметров из seed и фиксированный список check ids. Добавить reset, который проверяет готовность страницы и отсутствие записи предыдущей попытки.

**Готово, когда:** любой тест можно запустить независимо; параметры воспроизводятся; повтор запуска не зависит от предыдущей сессии.

### Задача 3. Получить полноценный baseline

Подключить журналирование действий, наблюдений, проверки и результат. Адаптер должен работать через текущий browse и сохранять сырой MCP-ответ. Запустить SAKAI-02 без накопленного навыка.

**Готово, когда:** есть полный успешный baseline с доказательствами каждого ожидаемого результата. Если baseline не получается, сначала исправить интеграцию и наблюдение; не маскировать проблему готовым вручную навыком.

### Задача 4. Добавить explorer и автоматическую валидацию

Запустить отдельную Pi-сессию, передать успешную трассу, сформировать `SKILL.md` и метаданные. Выполнить две валидации в новых сессиях, активировать кандидата по правилам раздела 9.

**Готово, когда:** происхождение навыка прослеживается до training attempt; кандидат содержит параметры; его принятие или отклонение происходит без участия человека.

### Задача 5. Реализовать повторение и сравнение

Добавить режимы A/B, раздельные seed для обучения/валидации/измерения, чередование порядка и заморозку навыка. Создать машиночитаемый и Markdown-отчёт.

**Готово, когда:** воспроизводимая команда формирует реальные трассы обоих режимов и отчёт с корректностью и стоимостью. Все метрики получены из запусков, а не заполнены вручную.

### Задача 6. Проверить негативные ветки и завершить P0

Проверить, что провал обязательного oracle исключает `PASS`, неуспешный кандидат не активируется, а timeout после потенциального Save не вызывает слепой повтор.

Для этого достаточно узких unit-проверок агрегатора результатов/состояния кандидата и контролируемой fault injection в адаптере. Не добавлять большой тестовый каркас, повторяющий весь implementation. UI-поведение подтверждается реальными прогонами Sakai.

**Готово, когда:** критерии раздела 14 выполнены, ограничения и незавершённые пункты честно указаны.

### Задача 7. Опционально добавить P1

Только после готового P0 сформировать исполняемую процедуру и провести отдельное сравнение B/C. Сохранить независимый evaluator и наблюдаемость подшагов. Если безопасное восстановление и трасса не обеспечены, оставить процедуру экспериментальной.

### Предлагаемое распределение модулей

| Модуль | Ответственность |
|---|---|
| `browser-adapter` | Вызовы реального browse, нормализация ответов, read-only наблюдения |
| `sakai-cases` | Сценарии, параметры, check ids |
| `attempt-runner` | Reset, новая Pi-сессия, бюджеты, итог |
| `trace-writer` | JSONL и ссылки на evidence |
| `skill-distiller` | Explorer-сессия, запись кандидата |
| `skill-validator` | Проверка кандидата и активация версии |
| `experiment-runner` | Фазы, парные seed, режимы, очередь |
| `reporter` | Сводка корректности и затрат |

Это логические обязанности; не требуется создавать отдельный сервис или пакет для каждой строки.

## 13. Что должно остаться после реализации

1. Изменения в существующем харнессе и краткое описание точек интеграции.
2. Четыре теста на естественном языке и воспроизводимый генератор данных.
3. Worker/explorer промпты.
4. Команды запуска smoke, обучения/валидации и сравнения, проверенные в реальном окружении.
5. Шаблон конфигурации без секретов: target URL, подключение к имеющемуся browse, модель, бюджеты, seed, каталог артефактов.
6. Реальные трассы A/B, результат автоматической валидации и версия извлечённого навыка.
7. `comparison.json` и `report.md` с полной картиной успехов, ошибок и затрат.
8. README с инструкцией повторения и перечислением фактических ограничений.

Названия CLI-команд определяются существующим проектом. В README указать реально реализованные команды; не выдавать предлагаемые интерфейсы за доступные.

Если модель или browse недоступны, можно завершить интеграционный код и локальные проверки, но нельзя утверждать, что обучение, UI-тесты или ускорение подтверждены. В отчёте должны быть точный блокер и команда для продолжения.

## 14. Критерии готовности P0

- [ ] Используется Pi и фактически установленный opencode browse; Playwright не добавлен.
- [ ] Стенд и версия/окружение зафиксированы; reset проверен.
- [ ] Четыре сценария независимы и содержат явные ожидаемые результаты.
- [ ] Есть успешная полная training-трасса SAKAI-02.
- [ ] Навык получен explorer из этой трассы, а не написан разработчиком вместо обучения.
- [ ] Автоматическое продвижение и отклонение кандидата работают.
- [ ] Свежий worker подтверждённо применил активный навык на других данных.
- [ ] A/B отличаются доступными знаниями; модель, инструменты и проверки сопоставимы.
- [ ] Измерения проводятся с замороженным навыком и без переноса истории сессии.
- [ ] Повторы, ошибки, fallback и затраты обучения отражены в отчёте.
- [ ] Неполные доказательства и превышение бюджета не превращаются в `PASS`.
- [ ] Команды и артефакты позволяют воспроизвести результат.
- [ ] Вывод про ускорение соответствует измерениям; область применимости ограничена проверенными сценариями.
